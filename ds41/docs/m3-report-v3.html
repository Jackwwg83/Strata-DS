Strata-DS 夜间报告：decode 提速（CUDA Graph + 混合流式）与 SAGE 1.59bpw

2026-10-07（凌晨） · DeepSeek V4.1 Flash · SAGE 1.59bpw（专家 101.4 GiB）· RTX 4090 + 128 GB 内存模拟 · feature/ds41 56929a3
一页结论
  • Decode 快了约一倍：同一段 200 token 的代码文本，8 线程 81.4 → 42.3 ms/token（12 → 24 tok/s），16 线程 62.2 → 40.3 ms（16 → 25 tok/s）。来自：落空专家一部分经 PCIe 送进 GPU 算（混合流式，你批准的偏离上游的设计）、整步 CUDA Graph、wo_a 改 FP8。
  • Decode 速度取决于显存命中率：代码文本命中 72% 时 40 ms；在扫描用的仓库文本上连续生成，命中只有 52%，是 52–77 ms（13–19 tok/s）。上游 Qwen 是 46–93 tok/s，我们还差 2–4 倍。
  • Prefill 长上下文到上游同一水平：32K 1,100、64K 1,159、128K 1,263、256K 967 tok/s（上游 Qwen：RTX 5070 2,107–2,171，Strix Halo 1,320–1,370）。
  • 1.59 的质量损失是真的，不是引擎 bug：5 篇文档平均 nll 比 3bpw 高 0.29（困惑度高约 34%），通用中英文损失最大；FP16 原型对同一个包算出 2.513，我们的引擎 2.509，一致。
  • 今晚试过但没合并的：新的 CPU 调度（开了混合流式后反而慢 5–15%）、跨层预取（预测准确率 53%，浪费 PCIe 带宽，反而慢 20–30%）。数据都在下面。
  • 投机解码的基础设施做好了：多 token 验证器 + 后缀投机，12 项正确性测试全过，投机输出和普通输出逐个相同；但在 PCIe 受限时提速只有 +5%（重复多的文本），重复少时反而 −10%，所以默认关闭。
  • 等你拍板：是否合并到 main / 发版；DSpark（官方 MTP 草稿网络，7.9 GB）放哪；3bpw 测试机怎么办（旧机器宿主坏了）。

Decode：今晚每一步的提升（实测）

同一篇 200 token 的代码文档逐 token 喂入，SAGE 1.59 包，所有专家常驻显存或内存（不读 SSD），显存命中约 72%。单位：毫秒/token（越低越好），括号里是 tok/s。

做法8 线程16 线程30 线程
今晚之前：落空专家全部 CPU 算81.4（12.3）62.2（16.1）52.4（19.1）
+ 整步 CUDA Graph（结果逐位相同）短上下文无变化短上下文无变化32K 上下文 81.8 → 65.2
+ 混合流式 v1：GPU 直接经 PCIe 读内存里的专家（配额 3）47.144.943.9
+ 先整块拷进显存再算（暂存拷贝，配额 4）42.3（23.6）40.3（24.8）41.2（24.3）

wo_a 改 FP8（每层 73.1 → 38.5 µs，约省 1.4 ms/token，结果逐位相同）在上面所有行里都已包含。

为什么 CPU 少了线程反而受益最大：混合流式把每 token 约 60 个落空专家交给 GPU（每个经 PCIe 约 0.26 ms），CPU 只剩约 5 个。CPU 核越少的机器，原来越慢，提速越大。

现在的瓶颈：nsys 时间线（16 线程）每步：把专家拷进显存 19.3 ms、稠密 GEMV 7.3 ms、等 CPU 5.1 ms、GPU 空闲 7.4 ms。PCIe 4.0 实测 26.3 GB/s 已跑满。下一步能动的：提高显存命中率（每少一个落空专家省 0.26 ms）、投机解码（一次前向出多个 token）、稠密 GEMV（dots 在做）。

引擎和原型一致（2.509 对 2.513），所以损失来自 1.59 量化本身。损失约为困惑度高 34%，通用中英文最大，代码最小，和作者的结论方向一致。生成样例（代码、英文、数学）读起来正常。

投机解码：多 token 验证器 + 后缀投机（已合并，默认关闭）

验证器一次前向检查最多 4 个 token，保留正确的前缀，回滚其余的状态（128 槽窗口、压缩器的半组、压缩 KV、Engram 历史）。草稿来自后缀匹配（照上游 SuffixDrafter：在已输出的内容里找重复片段），不用额外权重。DSpark 没有接入。

收益小的原因：现在 decode 卡在 PCIe 拷贝上。一个窗口验证 4 个 token，4 个 token 各自的专家重叠不多，要拷的量接近 4 倍。上游的投机解码收益大，是因为它的专家几乎都在显存/内存里、算得快。所以默认关闭（--spec none），需要时用 --spec suffix。

对 DSpark 决定的影响：DSpark 的接受率会比后缀匹配高，但在 PCIe 受限的情况下，验证窗口本身就贵，草稿再准，提速也有限，还要占 7.9 GB 显存（方案 A）或更多 PCIe（方案 B）。所以仍建议方案 D：先不接 DSpark，等显存命中率提上来（例如 32 GB 显存的卡）再评估。

注意：真实配置下（显存层自适应换入换出），开不开投机，同一个专家可能一次在 GPU（FP16）上算、一次在 CPU（int8）上算，贪心输出在接近平票处会分叉。固定驻留时输出完全一致（上面的端到端测试）。

今晚试过、没有合并的（附数据）

尝试结果决定
CPU 专家调度改成上游 ExpertPool 的切法（Codex）正确性全过；但开混合流式后 decode 反而慢 5–15%（16 线程配额 3：50.4 对 43.8 ms）。CPU 时间里约 37 of 46 ms 是 EXL3 解码本身，调度救不回来。不合并，分支 feature/ds41-cpu-experts 保留（含 5–8 行的修复，验证器以后可能用）
跨层预取：用下一层路由器提前预测并拷贝专家（Codex）结果逐位相同；但预测准确率只有 53%，浪费 PCIe 带宽，还占了显存槽：16 线程 52 → 65 ms。不合并，分支保留
dots：K1c-09 小矩阵 GEMV、K7-11 hc 混合K1c-09 快 1.8–2.5%（未到 3% 合并线）；K7-11 慢 12%。不合并；已给 dots 明确目标（小矩阵 m=1 提速 25–30%）

等你决定的事

1. 发版

feature/ds41 已推送（Graph + 混合流式 + 验证器 + 本报告）。我没有合并到 main、没有打 tag。建议：先开 PR 到 main 做一次完整评审，安装程序和服务端支持 DS4.1 之后再正式发版。

2. DSpark 放哪

1.59 包里带了 DSpark：3 层草稿网络，每层 128 个专家（MXFP4，共 7.2 GB），加上注意力等共 7.9 GB。一次草稿要跑 5 个位置 × 3 层。

方案好处代价
A. 全部放显存草稿最快24 GB 卡上主模型的显存层从约 11.5 GiB 降到约 3.5 GiB，命中率大跌，每个 token 多走很多 PCIe
B. 专家放内存，经混合流式算不占显存一次草稿最多约 45 个专家 × 18 MB，走 PCIe 约 30 ms，比省下的还多
C. 只放最热的 DSpark 专家进显存，其余 CPU 算折中要写 MXFP4 的 CPU kernel
D. 先只用后缀投机（不用 DSpark），实测接受率后再定（推荐）不占显存、不多读内存；代码和重复文本接受率高普通对话接受率低

3. 3bpw 测试机

旧的 3bpw 机器（54438962）宿主在 Vast 上一直显示离线，容器里还有卡死的进程占着 GPU，开机后无法使用，已再次停机（磁盘保留，约 $0.30/h）。选项：等 Vast 恢复；或另租一台（约 $0.4/h + 下载 3bpw 约 390 GB × $0.003 ≈ $1.2）。按你的规矩，租机器要你点头。
