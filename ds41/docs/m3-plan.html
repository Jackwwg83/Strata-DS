M3：批量 prefill

2026-10-06 · 已确认：单段和分段一起做；开一台便宜 GPU 机器用于编译和单元测试 · 依据：上游 src/prefill/prefill.cpp、src/program/generate.cpp、docs/DETAILS.md；DeepSeek 官方 ds41/proto/ref/model.py；exllamav3 v1.5.4 的 quant/。

一页结论

  1. 现状：引擎没有 prefill，提示词也是一个 token 一个 token 地过，约 3 token/秒。4K 的提示词要 20 多分钟。
  2. 做法：照搬上游。提示词一次进 GPU，40 层全在 GPU 上批量计算，CPU 不算 prefill 的专家。显存里有的专家直接用；没有的，经 PCIe 从内存拷进 GPU。拷贝走一个借用显存缓存槽位的环形缓冲区，和计算重叠进行。
  3. DeepSeek 特有的部分：注意力的窗口、KV 压缩器、indexer 的 top-k 和候选块、Engram、hc 混合，都要改成批量版本。官方参考实现只支持「从位置 0 开始一次处理完」，所以分两步：
    • 第一步做单段 prefill（上下文 ≤ 8K），语义和官方完全一致，可以直接和原型的 oracle 逐层比对。
    • 第二步做分段 prefill（16K 以上），这部分官方没有实现，需要我们自己推导。
  4. 速度预期（推算）：3bpw 的专家共 190 GB。批量 prefill 时几乎每层的每个专家都会被用到，所以每处理一段，就要把约 190 GB 的专家从内存或 SSD 搬进 GPU 一遍。瓶颈是搬运带宽，不是计算：
    • 64 GB 内存的机器，大部分专家从 SSD 读（约 6.5 GB/s），一段约 25–30 秒。
    • 按这个算，4K 上下文约 150 tok/s，8K 约 300 tok/s；1K 约 40 tok/s；512 约 20 tok/s。上下文越长，越能摊薄搬运成本。
    这比现在快 7–100 倍，但比上游跑小模型时慢（上游的专家只有 23–50 GB）。所以SAGE 1.59 的 prefill 会快很多，原因是专家只有 101 GB，128 GB 内存能全部装下。
  5. 工作量：我写引擎部分，约 2–3 天。专家的批量 GEMM 原样搬 exllamav3 的现成 kernel，交给 Codex，做法和 K10 一样。
  6. 需要你确认 2 件事，见文末。

0. 分段的语义（已确认一起做）

定义：分段 prefill 的结果，等于把这些 token 按官方 decode 的规则一个一个处理的结果。官方的单段 prefill（start_pos == 0）本身就和逐个 decode 等价：

  • 窗口：第 i 个 query 看 [i−127, i]，和 decode 的环形缓冲区覆盖的位置相同。
  • 压缩器：整组池化，余数进状态。和 decode 每满一组压缩一次的结果相同。
  • indexer：每个 query 用 (i+1)//r 做因果遮罩，候选块也按各自的可见长度选，和 decode 相同。

所以段的起点 p0 > 0 时，套用同一套规则即可：窗口里早于 p0 的位置从上一段留下的环形缓冲区取；压缩器把上一段剩下的余数和本段开头的 token 拼成一组；indexer 能看到之前所有段压缩好的 key。验证：分段结果、单段结果、逐 token decode 结果三方对照。单段最长受显存限制（24 GB 卡约 8K），所以 16K/32K 必须分段。

2. 显存怎么分

  • prefill 期间，从显存专家缓存的末尾借出一部分槽位当环形缓冲区，上限和上游一样：最多借 90%，至少留 128 个槽位。
  • T 个 token 的中间结果：hc 流 40 KB/token，q 64 KB/token，indexer 的分数矩阵 T × T/r × 4 字节。8K 上下文合计约 1–2 GB，24 GB 的卡放得下；16 GB 的卡要把单段限制在 4K 左右（第二步分段之后就没有这个限制了）。
  • prefill 结束后，把借出的槽位还原成原来的专家，和上游一样。

3. 怎么验证

  1. 和原型比：原型（官方 model.py）对文档做的就是 prefill。拿同一篇文档，比较每层的 hidden、每个位置的路由和 logits，以及整段的 nll。prefill 一次就能给出所有位置的 logits，可以直接算 nll。
  2. 和我们自己的 decode 路径比：同一段提示词，prefill 之后接着生成，和逐 token 处理完提示词再生成相比，nll 应该在噪声范围内。注意两者不会逐字节相同：上游的 prefill 和 decode 也不相同，注意力的求和顺序不一样。
  3. 单元测试：窗口索引、压缩器池化、逐行 top-k、token 按专家分组，各自对照 CPU 参考实现。
  4. 测速：上下文 512 / 1K / 2K / 4K / 8K，各测 prefill tok/s，以及紧接着 decode 64 个 token 的速度。这就是你要的「不同上下文下 prefill 和 decode 速度」的图。

5. 待确认

  1. 先做单段（上下文 ≤ 8K），分段以后再做？单段和官方语义完全一致，能直接对照验证；分段需要自己推导，风险更高。报告里的上下文就测到 8K 为止。
  2. 开发期间要不要开一台便宜的 GPU 机器，用来编译和跑单元测试？我本机（Mac）没有 CUDA，Codex 那台也没有。如果完全不开机器，2–3 天写下来的代码一行都没编译过，到最后再上 GPU 一起调，风险很大。我建议开一台最便宜的（比如 RTX 3060，约 $0.10/h），只用来编译和跑小测试，不下载模型。用到模型的测试，等代码写好后再开正式的测试机。
