M4：3bpw 在 128 GB 内存上跑起来（内存预算 + SSD 层）

2026-10-05 夜 · 待确认的方案，尚未写代码 · 依据：上游 Strata v0.1.39 docs/DETAILS.md（Low-RAM mode、A RAM budget）与 src/core/expert_source.cpp、src/program/generate.cpp；本仓库 ds41/bench/results/2026-10-05-routing/full/analysis.json、ds41/bench/results/2026-10-05-m2/

一页结论

  1. 问题：3bpw 的专家共 190.5 GiB，128 GB 内存装不下。现在的引擎把 experts.bin 整个 mmap 进来，完全靠操作系统的页缓存兜底；在 128 GB 机器上，页缓存会被 engram 表（2 × 101 GB）和 dense 文件挤掉，专家频繁从 SSD 重读，速度无法预测。
  2. 瓶颈在 SSD：按路由 trace 推算（24 GB 卡、自适应缓存、无投机解码），每个 token 有 9.4% 的专家访问落到 SSD，SSD 读 44.7 ms，CPU 25.7 ms，GPU 14.0 ms，约 14 tok/s。所以 M4 的核心是让 SSD 读尽量少、并且和计算重叠。
  3. 做法：照搬上游的低内存模式，共五件事：内存预算层（最热的非显存专家锁在内存）、Lookahead 预取（算第 l 层时预测第 l+1 层并提前读页）、自适应换出时把专家写回内存空位、engram 表用 O_DIRECT 读、每步打印分层统计。
  4. 预期：SSD 读和计算重叠后，单 token 从「三者相加」变成接近「SSD 与计算取大」，推算 3bpw / 24 GB 从约 14 tok/s 提到 18–22 tok/s。这是推算，要在目标机上实测确认。
  5. 工作量与费用：写代码约 6–8 小时（不需要 GPU）；目标机实测约 3 小时，Vast 上 7950X + 4090 + 125 GB 内存的机器 $0.67/h，约 $2–3。
  6. 需要你确认 3 件事，见文末「待确认」。

2. 设计（逐项对照上游）

2.1 内存预算层 上游 --resident-budget-gib N

  • 启动时，按 profile 排名，把不在显存里的最热专家复制进一块锁定内存（mlock；驱动允许时用 cudaHostRegister 做成 page-locked），直到用满 N GiB。这样内存里放的正好是显存的补集，两层不重复。
  • N 默认 = 当前可用内存 − 4 GB 余量（上游同样留 4 GB），可以用参数覆盖。128 GB 机器上预计 N ≈ 100 GiB，约 7,700 个专家。
  • 剩下的专家留在 experts.bin 里，照上游的做法通过 mmap 和页缓存读取。
  • 需要改的地方：CPU 专家 kernel（exllamav3 moe_mul1）在注册时就把每个专家的指针固定下来了。一个专家在「内存副本」和「mmap」之间搬家时，必须能改它的指针。我会给 third_party/exllamav3_moe 加一个很小的 patch：exl3_moe_cpu_set_expert_raw(handle, expert, gate, up, down)，原子地替换一个专家的描述符。这个 patch 单独提交，和上游 vendored 代码分开，并配一个单元测试。

2.2 自适应换入换出时，内存层跟着变 上游 resident_stage_swaps

  • M2b 的自适应缓存已经能把专家换进显存。M4 再补一步：被换出显存的专家，从显存拷回内存，放进新换入专家原来在内存里的位置；新专家的内存副本随之释放。这样内存层始终是显存层的补集，换入换出不会多读 SSD。
  • 如果新换入的专家原来不在内存层（它在 SSD 上），被换出的专家就退回 mmap 层，不占内存预算。

2.3 Lookahead 预取 上游 RouterLookahead

  • CPU 算第 l 层专家的同时，一个辅助线程拿第 l 层的专家输入（doorbell 已经把它放在映射内存里），乘上第 l+1 层的 router 权重（每层 384 × 5120 bf16，40 层共 157 MB，常驻内存），取 top-k，预测第 l+1 层要用的专家。
  • 预测出的专家里，既不在显存、也不在内存层的，用 madvise(MADV_WILLNEED) 让操作系统提前把它们的页读进来（上游 Linux 上的做法；Windows 上用 PrefetchVirtualMemory）。只读页，算出来的结果不变。
  • 到真正计算第 l+1 层时：如果某个专家仍然要从 SSD 读，就在计算前用 8 个线程并行地把这一层所有缺的专家一次读进来（上游 STRATA_FETCH_THREADS），避免计算中途单线程缺页。
  • 预测准不准，引擎里实测统计（「预取命中」），不先假设。DS41_LOOKAHEAD=0 可以关掉，方便对比。

2.4 engram 表和 dense 文件不进页缓存

  • 两张 engram 表共约 202 GB，每个 token 只随机读 48 行（每行 256 B 权重 + 8 B scale）。改成 O_DIRECT 按 4 KB 对齐读，每步开头并行发出，不污染页缓存。直接复用上游现成的读取器 include/strata/platform/direct_file.hpp（Linux 上是线程池 + O_DIRECT pread，Windows 上是 I/O 完成端口）。
  • dense.bin（11 GB）上传显存后，用 posix_fadvise(DONTNEED) 把它的页还给操作系统。

2.5 每步分层统计 上游 --stats 的 expert tiers

每步输出：显存命中数 / 内存层命中数 / SSD 读的专家数和 MB / 读盘耗时 / 预取命中数 / 系统可用内存。所有结论都用这些实测数字说话。

3. 验证方法

  1. 单元测试（先写测试）：预算层的选择（显存补集、按排名、遵守预算上限）；换出时内存层的更新；exl3_moe_cpu_set_expert_raw 换指针后结果正确；O_DIRECT 行读取和普通 pread 字节相同；Lookahead 的 router 预测和 GPU router 一致（同样的输入）。
  2. 数值不变：专家放在哪一层，读到的字节都一样。关掉自适应换入（--adapt-every 0，让显存 / CPU 的分工固定）时，「全在页缓存」和「预算层 + SSD」两种模式的逐 token dump 必须逐字节相同。
  3. 目标机实测：7950X + 4090 + 125 GB 内存（Vast 报价 $0.67/h），3bpw：
    • 5 篇文档 × 200 token 的 teacher-forced 速度和 nll；zh_mail 聊天 decode 128 token。
    • N = 0（纯 mmap，现状）/ N = 自动 两组对比；Lookahead 开 / 关对比。
    • 记录：tok/s、每步分层统计、可用内存最低值、有没有 OOM。
    • 验收：无 OOM；tok/s 写进报告，和推算的 14 tok/s（无重叠）对比；数值检查通过。

5. 风险

  • 容器里的 mlock 上限：之前在 Vast 上跑上游 ctest，有一项就是因为 memlock ulimit 失败的。锁不住时退回普通内存（可能被换出），并在日志里明确告警；在报告里注明。
  • Vast 上「125 GB」不一定等于真正的 128 GB PC：容器的内存上限和宿主机的页缓存策略可能不同。报告里会写清楚测试环境，不把它说成用户 PC 的结论。
  • Lookahead 的预测可能不准：DeepSeek 第 l+1 层的输入和第 l 层不同。上游在 Qwen 上有效，在 DS 上必须实测；如果预取命中率低，就只保留「批量并行读盘」，这部分不依赖预测。
