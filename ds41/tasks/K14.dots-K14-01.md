# K14-01: four-query tensor tiles and exact parallel row selection

Base: `7025587510974316112f3d1af1b559ea4de85dbe` (`origin/feature/ds41`, fetched 2026-10-06)

## Strategy

Each 512-thread CTA computes four queries against 64 keys. Its 16 warps each compute 32 heads by 16 keys using
BF16 WMMA with FP32 accumulation. Keys are loaded once for the four queries. The full query tile uses 32 KiB of
shared memory and the key tile uses 16 KiB. After every warp finishes reading the queries, a barrier permits reuse
of the query storage for the FP32 dots. Total static shared memory is exactly 48 KiB, so no dynamic shared-memory
opt-in or device-property query is needed.

Per-head dot rounding, ReLU, BF16 product rounding, ascending-head FP32 accumulation, and the final BF16 conversion
remain distinct, as in `ops::indexer_scores`. As with merged K5's tensor scorer, the tensor dot accumulation order
can differ from the scalar reference; the unchanged GPU acceptance thresholds still decide parity. There is no
approximation to the rounding stages, tie policy, or selection cardinality.

Scores are stored as BF16 in caller workspace. Each row's exact two-byte radix cutoff and ordered emission are
handled by one CTA, in parallel across rows. The positional scan uses K5's four-part, warp-prefix ordering; every
output index is `position + offset`, emitted ascending. All score ties, including masked `-inf` scores and signed
zeros, prefer lower positions. The output is padded with `-1` only after `min(k, t_i)` entries.

Candidate selection runs as another parallel row kernel. Block maxima are BF16 values or infinity, so the same
two-byte ordering is exact. The last block receives infinity, ties prefer lower blocks, and selected `-inf` blocks
are dropped, matching the fixed reference. Only `[0, t_i)` is written, including a partial last block; candidate
row padding is never initialized or overwritten. `topk_blocks <= 0`, all-block selection, arbitrary positive block
sizes, empty rows, and query/key tile tails have explicit paths.

## Workspace and graph contract

For `t_max > 0`, the workspace is:

`min(m, 256) * t_max * sizeof(BF16) + 255` bytes

The extra 255 bytes allow 256-byte alignment inside even a byte-aligned caller buffer. Empty contexts need zero
workspace. At the ranking shape (`m=4096`, `t_max=8192`), the requirement is 4,194,559 bytes, about 4 MiB. The batch
size bounds the number of stored query rows; it does not truncate the context or restrict processing to acceptance
shapes. Every query and every visible key is processed.

The host loop advances by 256 query rows, with two launches per batch (three with candidate output), instead of
launching scoring/selection once per query. Thus the 4096-query ranking case uses 32 launches. Workspace is reused
only after all same-stream consumers of a batch finish. Calls and graph replays have no internal allocation, free,
host/device copy, host synchronization, global scratch, or eager-call lifetime dependency. The zero-context path
uses only an asynchronous output fill on the supplied stream.

Shape, workspace, candidate stride, pointer-span multiplication, output-index range, and workspace alignment slack
are validated before any launch. Position sums are promoted before addition, so `pos0 + m` does not overflow int.
Representable negative offsets are supported. Inputs whose required int32 output positions or pointer spans cannot
be represented are rejected, rather than silently wrapping. The declared `m=1..16384` interface bound is enforced.

The branch was rebased onto the current M3 engine base before publication. Its stricter per-query acceptance check
is preserved unchanged.

  calls, including undersized/null workspace, invalid dimensions/stride/block, null inputs, and overflow rejection
- `check_selection.py`: ordering of all 65,282 non-NaN BF16 encodings, 496 exact top-k cases, 2,500 exact candidate
  cases, and 21,828 causal/workspace row checks passed
- `git diff --check` passed

The CPU selector harness models the radix/ordered-scan algorithm; it does not execute CUDA kernels and cannot
establish GPU numerical parity, races, graph capture, or speed. No speedup is claimed before queue results.
The unchanged fixed test includes the required candidate-layer capture/replay check. Queue acceptance remains
99.5% aggregate top-k overlap, at least 98% overlap for every query, and at most 0.1% differing candidate-mask entries. The published RTX 3060 baseline is
192,123 us at 4096 queries and 20,890 us at 512 queries; K14-01 has no measured GPU time yet.

```sh

nvcc -std=c++17 -O3 -arch=sm_86 -I include \
  src/ds41/kernels/k14/check_host_contract.cu /tmp/k14.o -o /tmp/k14-host-check
/tmp/k14-host-check
```
