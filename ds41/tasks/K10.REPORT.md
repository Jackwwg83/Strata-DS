## Selected configuration and rejected alternatives

Gate/up now uses CFG0 plus a new KSPLIT8 override: 256 threads, WK8, WNT2,
PF4 and FOLD4. This tuple is new, although eight-warp k-splitting is supported
by the upstream template's CFG1. The existing CFG1 is unsuitable because it
also changes WNT to 4 and the FP16 fold cadence to 2. Down retains the exact
K10-01 512-thread/WK16/WNT2/PF4/FOLD4 configuration.

Gate/up K5120 has 320 slices. Splitting them 16 ways gives 20 slices and 5 folds
per warp; splitting 8 ways gives 40 slices and 10 folds. Every original group
of four FP16 MMA slices is unchanged. Down K2304 has 144 slices, so a 16→8
change would turn nine-slice chunks into 18-slice chunks and move FP16 fold
boundaries. That change is rejected.

Trellis-load addresses, per-warp 32-lane shuffles, decoder/codebook, FP16 MMA,
four-slice fold statements, row guards, null-job guard and cross-warp reduction
statements are unchanged. Reduction has 8 terms for gate/up rather than 16.
All activation, BF16/FP8 rounding, Hadamards, slot order, caller workspace and
supplied-stream pipeline code remain byte-identical to K10-01. There are still
five launches per call; no allocation or host synchronization is added.

## Compile and resource evidence

CUDA 12.8, C++17, O3, sm86/89/120. Final gate/up three-block bound:

| Architecture | Gate/up registers | Gate/up shared bytes | Down registers | Down shared bytes | Spill stores/loads |
|---|---:|---:|---:|---:|---:|
| sm86 |79|1024|63|2048|0/0|
| sm89 |79|1024|63|2048|0/0|
| sm120 |76|1024|62|2048|0/0|

sm120 reports an 8-byte stack frame but no spills. All kernels are below 99 KiB.
A four-block gate/up bound compiled at 64 registers on sm86/89 but introduced
8-byte spill stores and loads; it was rejected. It had 62 registers and no
spills on sm120. The three-block bound is selected consistently for this
one geometry ablation. Register-limited theoretical residency on sm86/89 is
three 256-thread CTAs/24 warps versus K10-01's two 512-thread CTAs/32 warps.
Smaller CTAs and reduced cross-warp reduction compete with fewer active warps
and longer per-warp chains. These are tradeoffs, not measured speedups.

## CPU evidence and numerical risk

- Provenance: all 13 pristine upstream SHA256 hashes, reverse/forward patch
  roundtrip, identical helpers and decode/MMA/fold/reduction core after only
  the explicit WK override is normalized
- Address model: each 1,105,920 uint32 trellis words read exactly once for each
  fixed projection shape, plus identical activation/scale bounds
- Actual extracted source ring/partition model: K0..32768 in 16-element steps,
  no duplicate/missing/out-of-range slice or prefetch load
- K5120: exactly the same 80 four-slice FP16 groups; K2304 split 8 explicitly
  fails group equivalence and is not dispatched
- 100,000 arbitrary finite-half fold vectors with exponents 10..20: 14 changed
  outputs, relative L2 3.4042827e-9, max absolute delta 6.10351562e-5
- 100,000 vectors spanning all finite-half exponents: 65,739 changed outputs,
  relative L2 9.83051621e-8, max absolute delta 0.09375, worst nonzero-reference
  scalar relative delta 0.00462962963
- Adversarial cancellation: original FP32 association gives 0 while the new
  association gives 5.96046448e-8. No universal relative-error guarantee follows
  from this model
- Down GEMV and all three pipeline kernels have identical normalized PTX to
  K10-01 on all three architectures (only symbol/comment/function-label names
  are normalized)
- Caller workspace layout and all 32,640 finite nonnegative BF16 maxima pass
  the unchanged host layout/scale checks

The rounding model assigns arbitrary finite FP16 values to identical folded
MMA groups, then rounds each actual FP32 addition. It does not emulate CUDA
MMA products, real packed experts, nonlinear activation boundaries or final
MoE output. CPU evidence is not golden parity. The fixed GPU golden test and
its m1 non-default-stream graph check must pass before this is a candidate
for merge; no performance or graph-execution claim is made.
