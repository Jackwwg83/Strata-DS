## Design and exact preserved math

The narrow 3-bit mul1 GEMV now copies four K slices into a warp-private shared
buffer with `cp.async.ca.shared.global` while decoding the preceding four
slices from its other buffer. There are two buffers, each with 16 warp regions,
four slices and 48 uint32 words per slice: 24 KiB in total.

Only the instantiated K10 narrow integer path enables the new template flag.
The original register-prefetch implementation remains for all other template
configurations. The K10 launch retains 512 threads, 16 K splits, two N tiles,
MMODE=0, and a two-block launch bound. No launches were added.

1. Each lane below 24 copies its original two uint32 words per slice; every
   copy has the original four-byte alignment requirement. No vector overread,
   rounded-up tail, zero-fill read or new 16-byte alignment condition is used.
2. Copies are guarded by `first + d < myn`. The first four-slice group is
   committed before the loop. Each loop waits for its own completed group,
   executes a warp barrier, then commits the next group to the other buffer.
3. Each lane loads its own words from shared memory. The existing lane shuffles,
   trellis/codebook decoder, FP16 MMA instructions, accumulators and folds stay
   unchanged. K slices are consumed in increasing order and folded after the
   same fourth slices and final partial slice.
4. A buffer is reused only after its previous consumers finish. There is no
   shared-memory cross-lane handoff: the original shuffles distribute words.
   Completion uses `wait_group 0`, not a warp barrier alone. At most one group
   is outstanding during arithmetic; none remains at the cross-warp reduction.
5. The original cross-warp FP32 reduction, null-job guard, five-launch pipeline,
   activation/QDQ casts, all Hadamards, caller workspace, supplied stream and
   ordered output accumulation are unchanged.

The [CUDA 12.8 PTX specification](https://docs.nvidia.com/cuda/archive/12.8.0/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-cp-async)
defines four-byte `.ca` copies and per-thread committed-group completion.
All required targets support this sm_80-and-later instruction. The `.ca`
copy caches at L1/L2, unlike the original `.cs` streaming register load; cache
behavior is therefore another performance tradeoff that needs GPU measurement.

## Cost compared with register prefetch

K10-01 (`d42d168c`) has four live register-prefetch slots. K10-02 (`c05b95ba`)
has two slots while keeping four-slice arithmetic groups. K10-04 uses neither
register ring for its raw weights: asynchronous transfer bypasses those live
register values, then two shared loads per active lane/slice feed the unchanged
shuffles. It issues the next four slices before beginning the current four,
rather than refilling each individual register slot immediately before decode.

The tradeoff is 24 KiB additional shared memory, one commit/wait/warp barrier per
four-slice tile, and a shared write/read for each original raw packed word.
There are no additional CTA-wide pipeline barriers. Each legal gate/up warp
has 20 slices (five staged groups); each down warp has nine slices (three groups,
with one live slice in the last). Shared accesses are lane-owned and bank-distinct
within each individual load instruction.

Actual ptxas reports, same CUDA 12.8 compiler and flags:

| Candidate | Registers sm86 / sm89 / sm120 | GEMV shared bytes | Spill stores / loads |
| --- | --- | ---: | --- |
| K10-01 four-register-slot control | 63 / 63 / 62 | 2,048 | 0 / 0 |
| K10-02 two-register-slot control | 64 / 64 / 60 | 2,048 | 0 / 0 |
| K10-04 double-buffered async copy | 63 / 63 / 59 | 26,624 | 0 / 0 |

For K10-04 the stack is zero bytes on sm86/sm89, eight bytes on sm120, as in
both controls on sm120. The single allocated CTA barrier is the original
reduction barrier; warp synchronization does not allocate another CTA barrier.
The largest shared allocation is 26,624 bytes, below 99 KiB.

Two 512-thread blocks remain resource-feasible: each uses at most 64 registers
per thread and 26,624 shared bytes, or 53,248 shared bytes for two. This is a
resource calculation, not a measured achieved occupancy. Register allocation
on sm86/sm89 is no better than K10-01, so this candidate must earn back its extra
shared traffic and synchronization through transfer overlap. It may be slower.
Retaining it as a distinct experiment is justified by the actual async-copy
code generation without spills or loss of two-block resource feasibility;
no performance conclusion can be drawn until the GPU queue runs.

## Validation performed

- CUDA 12.8 C++17 kernel compilation for sm86, sm89 and sm120, without fast math
- PTX plus ptxas assembly for all three targets: actual async-copy instructions,
  group commits and waits present; no register streaming loads in the active
  K10 GEMV instance
- CPU extraction of the actual candidate C++ scheduling code, replacing only
  hardware copies/waits with symbolic eager/delayed completion: 26,816 lane,
  warp, tail and fallback cases; every original packed word loaded once, no
  invalid shared/global read, exact increasing slice and original fold order
- Twelve mutation probes reject decoder constant, K-split, FOLD, tail/lane
  guard, wait depth, buffer index, MMA operand, tail fold, reduction order and
  empty-job changes; activation reassociation is also detected
- Exact source normalization permits only the explicitly listed scheduling
  edits; its result must equal the merged adapter's SHA-256, so arbitrary
  arithmetic changes cannot hide inside an excluded source region
- Reverse/forward vendor-patch round trip restores all 13 pristine upstream
  SHA-256 hashes; decoder, MMA, fold and reduction source matches upstream
- Both legal packed-weight address maps, caller workspace bounds, all 32,640
  finite nonnegative BF16 maxima for scale rounding, native C++ workspace layout,
  fixed-file scope and no-allocation/no-host-sync source audits pass
- The fixed acceptance source, including its new graph test, compiles and links
  directly with the kernel archive and pack loader on all three targets; this
  is not a full CMake engine build and none of these executables was run
