# K10 report

## K10-02 compile-only prefetch experiment (2026-10-05)

This section supersedes the historical implementation report below for branch
`task/K10/dots-K10-02`, based on feature commit
`f75130394c5b56f0a72f20d04b2a06165a543c17`.

The experiment reduces the narrow weight-prefetch ring from four slices to
two. Arithmetic still traverses four-slice unrolled groups and folds FP16
accumulators to FP32 at exactly the original positions, including partial
last groups. The ring is indexed by the compile-time expression `d % PF` and
refills a slot two iterations before that slot is consumed again. A static
assertion requires the ring depth to divide the arithmetic unroll.

The 512-thread narrow kernel also requests two resident CTAs, matching the
resource target of the independent K10-01 launch-bound experiment. Unlike
K10-01, this branch changes prefetch scheduling. It preserves all 16 K-split
warps, two N tiles, decode/MMA operations, fold bodies, reduction order, five
launches, caller workspace and supplied stream. No allocation, host wait,
new dependency, fixed-interface or acceptance-test change is introduced.

| sm_89 | 64 | 2,048 B | 0 / 0 B | 0 B |
| sm_120 | 60 | 2,048 B | 0 / 0 B | 8 B |

All four entry points have zero spill stores/loads; maximum shared memory is

emit CUDA warning 20012-D. sm_120 has the reported 8-byte stack frame; no
zero-stack claim is made for that architecture.

The original sm_89 build used 79 registers and no spills. Compile-only local
alternatives were: two-slot ring/four-slice unroll with original launch bound
80 registers; two-slot ring/two-slice unroll with original bound 79; two-slot
ring/two-slice unroll with two-CTA bound 63. The published candidate retains
the four-slice unroll to avoid a runtime-dependent fold test and uses 64
registers with the two-CTA bound. These compiler counts are not timings.

`CXX=g++ python3 src/ds41/kernels/k10/check_host.py` passes:

- All 13 pristine SHA-256 hashes and reverse/forward vendor patch round trip
- Arithmetic byte comparison after enumerated prefetch-schedule normalization
- Ring contents, single-load coverage, consumption order and fold boundaries
  for 516 combinations of narrow/wide fold cadence and work lengths 0..257,
  including the K10 warp chunks of 9 and 20 slices
- Existing indexing, workspace, launch source, scope, scale rounding and C++17
  layout checks

`git diff --check` passes. The vendor patch was regenerated as a zero-context
unified diff so context-only blank lines do not introduce trailing whitespace;
its reverse/forward reconstruction is validated by the same hash checks.

GPU golden acceptance, CUDA graph replay, sanitizers, queue CMake build and
timing have not been run. The GPU queue is offline. This is a published
experiment awaiting the exact-SHA queue result, not a measured improvement.

## Implementation

The implementation includes the vendored `.cu` from the fixed K10 translation
unit. It uses five launches on the caller's stream:

1. Input Hadamards for gate and up, and device job descriptors for all slots.
2. One batched 3-bit mul1 GEMV for both projections.
3. FP32 output Hadamards, clamps, SiLU and FP32 routing weight, BF16 rounding,
   block-32 E4M3 quantize/dequantize with power-of-two scales, BF16 then FP16,
   and the down projection's input Hadamard.
4. One batched GEMV for the down projection.
5. FP32 output Hadamards and addition to existing output in slot order.

Each GEMV job retains upstream MMODE=0 / CFG=0, FP16 MMA accumulation and
four-step folding to FP32. The helper functions and entire main GEMV arithmetic
are byte-identical to upstream. Hadamard helpers, codebook and trellis decoding
files are unchanged. Scale-vector addressing keeps the upstream helpers'
`blockIdx.y` convention. Empty slots write null jobs and skip every projection
and any read of their scratch output; no empty-slot scratch needs initialization.

The caller workspace holds descriptors, input transforms, gate/up outputs,
down inputs and down outputs. For m=1/4/8 and topk=6 it uses
384,384 / 1,537,536 / 3,075,072 bytes. Buffers are aligned and disjoint; the job
table is reused only after the previous GEMV on the same stream. Valid calls
perform no allocation, host synchronization, device query, cooperative launch,
output reset or atomic output addition. Separate workspaces allow independent
streams; graph capture/replay remains to be validated on GPU.

The declared shared arrays total 2,052 bytes in the instantiated GEMV, 1,280 in
the activation stage and 512 in the output stage. Input transform has no shared
array. These are source counts, **not ptxas resource measurements**; compiled
shared memory/register usage and the 99 KB requirement remain unverified.

Only the requested 3-bit mul1 shapes are supported. Host arguments and scratch
size/alignment are checked before launching. Device descriptor assertions
check dimensions/rate/pointers when assertions are enabled. See
K10.QUESTIONS.md for the dispatch and error-handling interpretations.
