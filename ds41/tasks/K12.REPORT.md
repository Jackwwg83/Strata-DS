## Implementation

The new unity translation unit includes an adapted copy of upstream
`quant/reconstruct.cu`. The two new vendor files were first copied unmodified
from exllamav3 commit `16a49792a3c93d8432d72e6c4bce800841566577`; pristine
SHA-256 hashes were recorded before adaptation. Only the new files are patched.
The old K10 patch is an unchanged prefix of the extended reversible patch.

For each nonempty expert group:

1. Read its device descriptor into a three-entry device pointer table.
2. Reconstruct w1, w3 and w2 once into FP16 matrices in the Hadamard basis,
   using the unchanged upstream `reconstruct_tile<3, 2, false>` and batched
   kernel with one matrix per launch.
3. In tiles of up to 512 rows, gather x using the absolute token row indices,
   applying K10's input Hadamard/suh separately for gate and up.
4. Run two cuBLAS GEMMs with FP16 inputs, FP32 compute/output. Apply K10's
   FP32 output Hadamards/svh, clamp, SwiGLU, routing weight, BF16 cast,
   block-32 E4M3 quantize/dequantize, second BF16 cast, FP16 cast and down
   input Hadamard/suh.
5. Run the down GEMM, then its FP32 output Hadamard/svh and atomic scatter-add
   into the existing output. Only assigned tokens are touched.

The row-major GEMM is expressed as column-major C^T = B^T A^T with
`m=n`, `n=rows`, `k=k`, leading dimensions n/k/n and no transpose flags,
matching upstream `hgemm.cu`. Reduced-precision reductions are disabled.
No original-basis weight reconstruction is used, preserving the positions of
K10's Hadamard rounding. The activation arithmetic/casts are source-compared
against K10, with only `weights[slot]` changed to `weights[row]`.

A process-lifetime cuBLAS handle is created on the first nonempty call per
device. Later calls use the supplied stream and workspace. A mutex protects
host handle mutation/enqueue across threads; no host synchronization with GPU
work is introduced. The caller must use separate workspaces for concurrent
executions. Empty groups/calls perform no work, and global offsets are kept
separate from tile-local scratch indices.

The maximum workspace is 107,741,695 bytes: three dense matrices (67.5 MiB),
512-row activation buffers (31.25 MiB), cuBLAS scratch (4 MiB), a 256-byte
pointer-table region, and 255 bytes of alignment slack. It is bounded even
for larger row/group counts. `cublasSetWorkspace` follows `cublasSetStream`,
which resets the workspace setting. The 4 MiB allocation and 256-byte
alignment follow [CUDA 12.8 cuBLAS guidance](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html#cublassetworkspace).

sm_86, sm_89 and sm_120) and run the fixed `k12_exl3_moe_prefill_test` linked
with K10 and cuBLAS. Required results remain:

- The T=37 CUDA graph capture/replay check after setup.

rounding can amplify these differences. Passing the numerical tolerance is
unknown, not inferred from source similarity or successful host audits.

architecture compatibility are likewise unverified locally.

No crossover threshold was measured; this can be inefficient for sparse
small groups. There is no performance claim. Changes for speed should follow
GPU correctness and timing evidence.
