# K15-02: FP32 weight reuse across 16-token, 3-row tiles

Base: `c19cf821cf1360db4c4b5239497412fe4dfc4319` (`feature/ds41`).
Branch: `task/K15/dots-K15-02`.

## Design

The producer tiles 16 tokens, 3 output rows and 4 original dot-product warps per
128-thread CTA. A weight is loaded once for 16 tokens; each BF16 x value is loaded
once for 3 independent FP32 dot accumulators. This deliberately uses ordinary
FP32 FMA, without rounding fn to BF16/TF32 or using approximate tensor-core math.
There are 8 row groups and 2 original-warp groups per token tile.

Each lane keeps the complete reference 80-term stride-256 accumulation chain.
The original shuffle reduction (16,8,4,2,1) produces its warp subtotal. The caller's
workspace stores `[token][24][8]` FP32 subtotals. Finish adds the 8 warps in order,
starting from +0, matching `ops::block_sum<256>`.

The second kernel assigns one 1024-thread CTA per token. Its loop order is
`j=0..3`, then `k=0..4`, at `x[j*5120 + k*1024 + tid]`. This exactly preserves the
reference norm's 20-term stride-1024 FMA chain. Each x load also feeds one of five
independent collapse accumulators, each in `j=0..3` order, with pre_in and one final
BF16 rounding. It reduces 32 norm warp totals in ascending order. Two CTA barriers
publish the shared dot/norm data and reciprocal RMS before the first warp finishes
coefficients.

The RMS multiplication is explicitly rounded with `__fmul_rn` before scale/bias.
All 32 lanes execute the coefficient shuffles, with lanes 16..31 duplicating the
4x4 matrix. Row and column sums are sequential, not tree-reassociated. Softmax has
its output epsilon; initial column normalization is followed by 19 row/column
pairs, each with denominator epsilon.

There are 2 launches at m=4096. Batches with both full tiles and a nonzero tail
require a separate guarded producer launch, for 3 total. Batches below 16 tokens
use only one producer plus finish, for 2 total. The m=1 specialization uses one warp/row per CTA. This base's
K15 baseline invokes K7 512 times at m=4096; K7 currently launches two kernels per
call. No performance improvement is claimed until the authorized queue measures it.

## Bounds and graph contract

- Workspace is 768*m bytes: 3 MiB at 4096, 12 MiB at 16384
- All 24*8 partial slots are overwritten for every valid token on every call
- Full/tail producers are disjoint; tail x reads and stores are guarded
- Inactive tail tokens still execute every warp shuffle
- Finish has no partial CTA or token: every lane maps to five legal y elements
- Capacity may exceed the actual m requirement, as needed by engine reuse
- Invalid m, null, undersized or non-float-aligned workspace is rejected on host
- No allocation, host synchronization, global scratch, device switch, spin, atomic
  publication or default-stream override occurs in the runtime
- All launches use the supplied stream; workspace lifetime and separation remain
  caller-owned, allowing independent calls to use independent buffers

## Validation completed locally

CUDA 12.8.93, C++17, `-O3 --ftz=false --prec-div=true --prec-sqrt=true`, GCC 12.2.
Fixed acceptance plus supplemental device test and host-rejection executable all
compile and link on sm_86, sm_89 and sm_120. No fixed header, test, ops, CMake,
K7 implementation, task contract or priorities file was edited.

Compiler resources (registers / user static shared bytes reported by ptxas):

| Kernel | sm_86 | sm_89 | sm_120 |
| --- | --- | --- | --- |
| Full 16x3 tile | 72 / 0 | 72 / 0 | 80 / 0 |
| Tail 16x3 tile | 71 / 0 | 71 / 0 | 128 / 0 |
| Single-token producer | 19 / 0 | 19 / 0 | 19 / 0 |
| Finish, 1024 threads | 40 / 228 | 40 / 228 | 40 / 228 |

Every kernel has zero stack, spill stores and spill loads. Maximum user shared
memory is 228 bytes. The sm_120 finish cubin reports 1252 bytes including 1024 bytes
of system shared overhead; its producers report zero shared allocation. The maximum
physical shared allocation is therefore 1252 bytes, still below 99 KiB. The 1024-thread finish uses 40,960 registers,
within the target architectures' per-block register limits. These resource counts
are compiler output, not occupancy/performance measurements.

Supplemental checks:

- CPU shared-schedule model: bit-identical dots, norm and BF16 collapse, and zero
  per-token coefficient error at m=1,2,15,16,17,31,32,33,37,300; separate zero-input
  m=17 and single-token-template checks pass
- CPU model also passes UndefinedBehaviorSanitizer with recovery disabled
- Ownership and bounds model: all workspace, norm and y slots covered once for
  m=1..33,37,300,4096,16383,16384; tail canaries remain intact
- Negative control: BF16 fn rounding gives worst per-token pre/post/comb errors
  0.000881 / 0.00120 / 0.00218, correctly rejected by the 1e-5 contract
- Negative control: splitting an 80-term FP32 chain changes a cancellation example
  from mix=1 to mix=0 and is detected
- Negative control: a 2.5e-5 per-token error can be diluted to 1.44e-6 at m=300;
  validation therefore checks coefficient errors separately for every token
- Host API checks on all 3 builds: workspace sizes, invalid counts, null/short/
  misaligned workspace rejection pass without launching GPU work
- PTX checks on all 3 builds: 1/48/48 complete producer FMA chains of 80 terms;
  three explicit rounded normalized-mix multiplications; two publishing barriers;
  five final BF16 collapse casts; no tensor or local-memory operations
- Diff scope, protected-file byte hashes and supplied-stream launch audit pass

The standalone build/check entrypoint is
`src/ds41/kernels/k15/build_checks.sh OUTPUT_DIRECTORY`. Source the local CUDA/compiler
environment first. The CPU model uses `-ffp-contract=off` and explicit std::fma.
Its host exp/sqrt arithmetic establishes schedule consistency, not GPU libdevice
parity. PTX checks similarly do not replace executing the generated cubin.
