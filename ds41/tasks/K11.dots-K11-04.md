# K11-04: dynamic small-batch CPU expert bands

Base: `origin/feature/ds41` at `f958b86a4a540981b28f7c14bd0925c47436da6d`.
This is a docs-only successor of the tested `1164a4b` control; numerical source,
public header, and fixed test are identical between those control commits.
Branch: `task/K11/dots-K11-04`.

## Status and acceptance caveat

This is a bounded scheduling experiment, not a measured target win. The cloud
mechanism test supports adapting to unequal worker throughput. Unmodified-cloud
m1 timing is inconclusive, and median summed GEMV worker CPU time increased from
57.4 to 64.9 ms (+13%). That extra CPU demand could hurt the complete engine.

The reviewer's all-RAM i9 sweep favors 24 workers (score 4823 versus 5256 at 8),
but actual engine 8-to-24-worker pairs regressed: 313.4 to 409.3 ms/token and
294.1 to 319 ms/token. Doorbell spinning, lookahead I/O, CUDA host work, and
file-faulted experts compete for CPU time. Therefore a queue microbenchmark pass
is insufficient: acceptance also requires an actual-engine win against the
8-worker control. If target performance regresses, retain the merged control.
No CPU default, requested thread count, affinity policy, or silent cap is changed.

## Change

- Gate/up and down GEMV phases claim complete 8-tile (128-column) bands from
  an invocation-local atomic cursor. Faster workers can claim more bands
- Apply only to AVX2/AVX-VNNI, input batches 1 through 8, more than one
  participating worker, and positive output tile widths divisible by 8
- Keep the original scheduler for scalar, every AVX-512 tier, single-worker
  execution, and larger prefill batches
- Reset the cursor only on the coordinator, between completed pool phases.
  Keep the existing phase barriers and global forward/pool serialization
- Keep prepared input arrays, persistent arenas, numeric kernels, wide-row
  second passes, folds, activation/clamping, and final accumulation order
- No new dependencies, heap allocations, worker scratch, CPU topology guesses,
  new thread pool, or expert-output reduction

The helper is in `strata_dynamic_schedule.h`. Marked changes in `moe_mul1.cpp`
add the context-local cursor, include the helper, change two scheduling calls,
and reset the cursor before the two relevant phase dispatches. The public
`moe_mul1.h` and fixed acceptance test are unchanged.

## Safety

A ticket identifies exactly one matrix and one aligned output band. Atomic
fetch-add makes claims unique; clipping at the total band count gives complete,
nonoverlapping coverage. The cursor uses int64 arithmetic. Relaxed ticket atomics
are sufficient because unchanged pool release/acquire dispatch and completion
barriers publish prepared data and drain all workers before reuse.

The cursor lifetime is the forward context's lifetime. It is never a global
cross-call queue. Host-thread-local arenas and the existing pool mutex preserve
independent concurrent callers' buffers. Every band still executes complete
`run_rows`, including both passes for wide rows. Final accumulation follows the
original expert/token order, independent of claim or completion order.

This does not guarantee that more requested threads improve performance. The
queue keeps those workers participating at all existing barriers. It cannot
remove CPU quota throttling, memory contention, SMT sharing, or engine I/O stalls.

## Cloud mechanism measurements

All timings below are synthetic, instrumented cloud measurements, not acceptance
scores. The experiment used 32 random 3-bit experts, H5120/F2304, top-k6,
seed11223344, normal input, suh=1, svh approximately .01, and silu limit10.
Current control and dynamic claims used identical arithmetic in one binary.
Other workers' benchmark/validation loads were stopped during measurement.

A bounded nine-quartet screen compared grains 1/2/4. Grain1 was retained for its
smallest slow-worker tail; the screen did not establish a fastest grain on the
uninjected cloud control. Confirmation used 21 fresh rotating control/grain1
pairs for m1, with and without an explicitly injected slow-worker condition.
The injection burned extra CPU on workers4–7 equal to their just-completed
GEMV callback CPU time. This tests artificial throughput imbalance; it does not
model i9 P/E cores, page faults, storage, CUDA host competition, or the engine.

| Confirmation, dynamic / control | Paired wall ratio | Descriptive bootstrap 95% interval | Critical-worker CPU ratio |
| --- | ---: | ---: | ---: |
| m1, no injection | 0.847 | 0.748–1.070 | 0.990 |
| m1, injected 2x workers4–7 | 0.584 | 0.544–0.629 | 0.563 |
| m8 round-robin, 9 pairs | 0.785 | 0.702–0.864 | 0.857 |
| m8 same-six experts, 9 pairs | 0.831 | 0.726–0.908 | 0.868 |

The CPU proxy is max worker CPU for gate/up plus max worker CPU for down; it is
not measured target latency. On injected m1, gate/up maximum/mean worker CPU
fell from 1.574 to 1.078, and dynamic workers4–7 took fewer bands. On uninjected
m1, critical-CPU uncertainty includes no gain and summed CPU rose 13%. The cloud
control's wall range was 7.54–24.51 ms. These intervals describe these samples;
they do not provide target guarantees. All 192 timed scratch outputs and 216
additional scratch correctness outputs matched bitwise.
