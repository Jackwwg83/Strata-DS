# K14-02: head-streamed larger score tiles

## Strategy

A 512-thread CTA scores 16 queries against 128 keys. It retains the key tile while
streaming heads 0..7, 8..15, 16..23, and 24..31. Each warp computes a 16-row matrix
(two queries, eight heads each) against four disjoint 16-key groups. The query
storage is reused for FP32 dots after a CTA-wide reader-retirement barrier. Each
thread retains four FP32 running scores across all groups, applying the two BF16
roundings per head before adding heads in their original 0..31 order. A single
final BF16 conversion produces each stored score.

Compared with K14-01's 4-query x 64-key CTA, this halves query global-load traffic
per query/key output and quarters key global-load traffic, before cache effects.
These are structural traffic ratios, not measured speedups. It uses four streamed
head groups and more barriers, so occupancy and synchronization remain GPU timing
questions. The 136-element BF16 staging stride distributes consecutive rows over
shared banks. Group weights are shared broadcasts instead of duplicated global
loads. The shared layout is 100,608 bytes (98.25 KiB), below the 99 KiB limit.

The exact two-byte BF16 radix selector is copied from independently reviewed
K14-01 commit `1e8f6d22166620116d76d81c1c00851f4b100285`, whose full production
file SHA-256 is `d061923b0df41325df17949a730cfb694b184f13e314f2a7a4def368d818a11e`.
The unchanged selector section SHA-256 is
`60ce0b447f57f5e893c758d42c6592f7f5585244f0c369cfbe0ba4d04911baae`.
This branch owns its copy and has no runtime/build dependency on that branch.
Top-k keeps lower positions for ties and emits ascending positions plus offset.
Candidate selection forces the last block to infinity, drops negative-infinity
blocks, and writes only the causal prefix. Signed zero scores compare equal.

## Workspace and capture

Caller-owned workspace holds at most 256 BF16 score rows, then is reused on the
caller's stream after both row-selection consumers. Its size is
`2 * min(m, 256) * t_max + 255` bytes for nonzero context, otherwise zero. The
255-byte allowance supports arbitrary caller pointer alignment. At the ranking
shape this is 4,194,559 bytes. Shapes, overflow, candidate stride, output indices,
and workspace spans are checked before device work.

No device allocation/free, host/device copy, device-property query, global scratch,
or host synchronization is introduced. All launches and the zero-context fill use
the supplied stream. `cudaFuncSetAttribute` opts the current device/function into
the fixed dynamic-shared size on each nonempty call. There is no persistent device
cache or initialization allocation. Actual CUDA capture/replay remains part of the
fixed GPU test; a CPU launch mock cannot establish capture safety.

## Remaining gate

Only the real GPU queue can establish acceptance and speed. The unchanged test
requires >=99.5% aggregate top-k overlap, >=98% for every query, <=0.1% candidate
mismatch, ascending/padded rows, candidate-tail preservation, and CUDA graph
capture/replay. WMMA changes the FP32 dot accumulation order relative to the
reference; head order and BF16 conversion boundaries are preserved. No GPU pass,
timing, speedup, or merge recommendation is claimed. The current RTX 3060 ranking
control is the merged K14-01 at 38,726.7 us (the original baseline was 192,123 us).
The >=3% speed gate is <=37,564.899 us against that control. The reviewer owns
acceptance and any merge.
