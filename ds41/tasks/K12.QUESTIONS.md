# K12 decisions and remaining validation questions

No question below blocks writing or reviewing the implementation. No response
was requested during this unattended task.

1. **Which many-row path should be used without GPU measurements?**
   Choose upstream trellis-only reconstruction plus cuBLAS, for every nonempty
   group. The trellis is decoded once per projection per group, and row tiles
   reuse the three dense matrices. This is a conservative implementation
   choice, not a measured crossover or speed claim. A small-row GEMV tier or
   fused GEMM can be added after the reviewer measures this version.

2. **Should reconstruction fold the Hadamards into the weights?**
   No. Use upstream `reconstruct_tile<3, 2, false>` and keep K10's input
   Hadamard with suh in FP16 and output Hadamard with svh in FP32. The fused
   original-basis reconstruction would move rounding to different locations.
   The K10 clamp, SwiGLU, routing weight, BF16, FP8 block-32 QDQ, second BF16
   conversion and FP16 cast are retained in the same order.

3. **Does cuBLAS have to reproduce K10's FP16 partial-accumulation folds?**
   Chosen interpretation: the explicitly permitted reconstruct + cuBLAS path
   uses upstream `hgemm.cu`'s FP16 inputs and FP32 accumulation/output; exact
   K10 fold order is not required, but the fixed 5e-3 GPU comparison is.
   Disable reduced-precision reductions. FP32 GEMM is not bit-identical to
   K10 GEMV. In particular, gate/up differences can cross BF16/FP8 rounding
   boundaries; whether the output passes the tolerance remains untested.

4. **How should graph capture and stream changes work?**
   Retain one cuBLAS handle per CUDA device, initialized on that device's first
   nonempty call before capture. A host mutex protects handle configuration
   and enqueue; it does not synchronize the GPU. Every call sets its stream,
   then supplies 4 MiB of caller-owned, 256-byte-aligned cuBLAS workspace.
   Concurrent calls/graph executions require distinct workspaces. Empty calls
   return without setup. Handles have process lifetime; CUDA context reset
   while cached handles are live is not supported.
   See [CUDA 12.8 cuBLAS workspace and graph documentation](https://docs.nvidia.com/cuda/archive/12.8.0/cublas/index.html#cublassetworkspace).

5. **Are row indices local to each call?**
   No. `tok + first` and `w + first` use the absolute offsets in the host
   array, including `off[0] > 0`. Experts are indexed locally with `experts + g`.
   Scratch rows start at zero for each tile. Empty groups launch nothing;
   atomics support duplicate token assignments and preserve unassigned rows.

6. **What workspace bound is appropriate?**
   Keep three reconstructed H-by-F FP16 matrices, activation scratch for at
   most 512 rows, and 4 MiB for cuBLAS. The query includes 255 bytes of alignment
   slack and a padded pointer table. The maximum returned size is 107,741,695
   bytes (102.75 MiB plus 511 bytes); it does not grow beyond 512 rows or with
   group count. Larger groups are tiled without repeating reconstruction.
   Negative limits are rejected; zero rows/groups need no workspace.
