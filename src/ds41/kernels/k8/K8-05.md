# K8-05: hierarchical GPU top-6

Based on `feature/ds41` commit `f75130394c5b56f0a72f20d04b2a06165a543c17`.
Only K8 CI-FILES are changed. The interface and fixed acceptance test are unchanged.

## Producer and merge

Each 256-thread producer CTA owns eight experts. Each warp reads one complete
5120-element BF16 weight row, reusing each loaded weight across all `m` tokens.
The producer computes the nonlinear score, selects its local six experts for
each token, and writes those candidates. A second kernel merges the 48 local
lists, keeps the global six in routing order, and normalizes their original
unbiased scores. All eight legal token counts have the same algorithm.

Eight experts per group is a structural choice, not a measured optimum:

- It is the smallest power-of-two group larger than top-6. Forty-eight independent
  producer CTAs retain more grid-level parallelism than 16- or 32-expert groups
  (24 or 12 CTAs), while providing one warp per expert and one warp per token
  during local selection
- The weight source traffic is one 384 x 5120 x 2-byte pass, 3,932,160 bytes, for
  any `m`. It is not an `m`-pass GEMV. Activation loads are not eliminated; the
  design relies on their small, repeatedly reused input working set
- The final merge sees 288 candidates per token rather than 384. At `m=8`, the
  task arena has 2,304 24-byte slots, exactly 55,296 bytes, including padding
- Candidate slots carry double biased and unbiased scores plus the ID. This is
  not a claim of less scratch than a plain FP32 logits array. Compared with
  materializing all 384 equivalent candidate records, it removes 25% of them
- Shared memory is at most 1,024 bytes per producer, so the design does not trade
  the local reduction for a large shared weight tile. The 48-block grid can still
  underfill a large GPU; this variant needs timing before performance conclusions

This is a two-level candidate-selection design, distinct from either writing all
expert scores to global memory or assigning the entire router to one CTA.

## Exact selection property and ties

For each token, order expert candidates by descending `s + bias`, breaking equal
scores by ascending expert ID. Both levels use this identical comparator. IDs
are unique, so it is a total order for non-NaN scores, including infinities.
NaN ordering is not defined by the fixed reference comparator either.

If an expert is not in the first six of its own group, at least six experts in
that group precede it in this total order. Those six also precede it globally.
Therefore it cannot be in the global first six. The union of group top-6 lists
contains every global top-6 expert. Taking the first six of that union with the
same comparator yields the exact IDs in the exact global order. In particular,
equal-score experts are never discarded in favor of higher IDs.

Each selection round reduces a maximum and removes only that winning ID.
Invalid lanes have score negative infinity and ID `INT_MAX`, so even a valid
negative-infinity expert precedes an invalid lane. There are always at least six
valid experts at either level. No candidate is duplicated across groups.

## Arithmetic preservation

`ops::bf16_gemv_k` assigns a row to a warp. Lane `l` accumulates, starting at
FP32 zero, the 160 products at indices `l + 32*j` in increasing `j`. The producer
uses exactly that sequence, with `__fmaf_rn`, separately for each token. Sharing
a loaded weight does not change any accumulator dependency. Each accumulator
then uses the same FP32 shuffle-down additions at offsets 16, 8, 4, 2, 1, with
explicit `__fadd_rn`. No tensor-core dot, split-K sum, BF16 accumulator, or
reassociated reduction is introduced. CUDA 12.8 PTX inspection confirmed the
reference uses `fma.rn.f32` and this shuffle/add sequence.

The resulting FP32 logit is promoted to double before `sqrt(softplus(logit))`,
matching the fixed acceptance reference's precision. Bias addition and comparisons
also use double, avoiding artificial FP32 score ties. Each candidate retains its
original unbiased double score; the final sum adds the selected scores in rank
order and applies `s / (sum + 1e-20) * 1.5`, then converts the output to float.
CUDA versus host transcendental implementations still require hardware numerical
validation; compilation and a selection proof are not that validation.

## Scratch and stream contract

A K8-private map is keyed by CUDA device ordinal. The first eager call on each
device allocates the entire 55,296-byte arena, even for `m=1`, and retains it for
the process lifetime. Warm calls only look up the pointer and enqueue the two
kernels on the supplied stream. There are no warm allocations/frees, host-device
copies, host reads of device results, or stream/device synchronizations.

This relies on the supplied engine contract that calls and graph replays of the
same task never overlap on one device. Different tasks can overlap because this
arena is private to K8; different devices have different allocations. The host
mutex protects map initialization/lookup and does not synchronize GPU execution.
The stream orders producer writes before merge reads. Every candidate consumed
is written by the current call; no clearing pass or previous-call contents are used.

## Validation recorded before publication

- CUDA 12.8 / C++17 source compilation: pass on sm_86, sm_89, and sm_120
- Producer register count: 40 on sm_86/sm_89, 38 on sm_120, for all `m=1..8`
- Merge register count: 44 on sm_86/sm_89, 39 on sm_120
- Producer static shared memory: 128 to 1,024 bytes; merge: 244 bytes on sm_86/89,
  248 bytes on sm_120. Dynamic shared memory: zero. All are below 99 KiB
- All compiled kernels report zero stack frame and zero spill stores/loads
- `python3 src/ds41/kernels/k8/validate_hierarchy.py`: 345 CPU selection-model
  rows pass, covering all legal `m`, all-equal scores, low/high ID ties, each
  group's concentrated winners, infinities, near-adjacent doubles, zero scores,
  the nonlinear threshold, and preservation of unbiased normalization
- Source whitespace check: pass

No CUDA device is available locally. GPU acceptance, actual graph capture/replay,
non-default-stream execution, sanitizer checks, and timings have not run. The GPU
queue is offline; this branch is a compile-checked candidate, not a measured winner.
