# K2-14: packet-sized shared publication

Base: `feature/ds41` at `b194191a2a3e5cada9ae4dedc96d48ad8d5a2f76`.
Runtime source SHA-256: `4f3f33efba8fc6cd7d900f35488f871657ba81748e063d7d391a05d29b3a00ba`.

## Change

The existing grouped 128x128 consumer is retained. In that path only, four
lanes cooperate on a weight column. Each lane reads eight packed FP8 bytes
at a time, and two column rounds cover the 128x32 weight tile. Each decoded
packet becomes four packed BF16 pairs, published with one explicit aligned
`st.shared.v4.u32`. The same full-linear-index XOR mapping is used by the
activation publisher, weight publisher, and both ldmatrix consumers:

`F(row, k) = (row * 32 + k) XOR ((row & 7) * 8)`

Each aligned K8 packet remains contiguous. The XOR permutes a row bit as
well as K bits, so applying it to K alone would be incorrect. A lane-zero
scale load and broadcast is performed separately for each packet round.
Each warp's eight columns in one round lie in one 32-column scale block.
The existing column guard handles arbitrary N tails, including the case
where a packet round has no valid columns.

This is a producer-ownership and publication-width experiment. Compact XOR
alone appeared in earlier K2 variants and is not a new claim. The unchanged
CUDA FP8 conversion produces FP32 values, followed by FP32 scale multiply
and round-to-nearest BF16 conversion. Packing the four BF16 pairs into raw
words does not change that sequence. No alternative FP8 decoder is used.

The 16x64 and 32x64 narrow paths retain their original padded shared layout,
sixteen-FP8 producer packet, scale broadcast, and scalar pair publication.
Activation quantization, dispatch, grouped CTA traversal, one-stage
prefetch schedule, barriers, MMA order, FP32 accumulators, output stores,
workspace usage, and supplied-stream behavior are unchanged. There are no
allocations, host synchronization, runtime queries, or mutable global state.

## Expected tradeoff, not a speedup claim

The address model predicts grouped publication service rounds per warp and
K32 stage change from A=16/B=32 to A=8/B=8. Matrix loads remain unchanged.
These are modeled shared-bank service counts, not measured cycles.

Weight bytes and conversion count are unchanged. Two eight-byte global
loads replace one sixteen-byte global load. Scale-load/broadcast count
doubles per warp, and one more scale value remains live across compute.
The grouped shared allocation decreases from 20,480 to 16,384 bytes, but
register pressure increases from the sm_86 control's 124 to 128 registers.
The existing two-CTA launch bound remains intact, with no spills. Hardware
profiling and repeated same-device timing are needed to establish whether
the publication change outweighs these costs.

## Cloud-only validation

CUDA 12.8.93 / GCC 12.2, C++17, `-O3 --ftz=false --prec-div=true --prec-sqrt=true`:

| Target | Grouped registers | Grouped shared bytes | 32x64 registers | 16x64 registers | Stack/spills |
| --- | ---: | ---: | ---: | ---: | --- |
| sm_86 | 128 | 16,384 | 58 | 54 | zero |
| sm_89 | 128 | 16,384 | 64 | 56 | zero |
| sm_120 | 128 | 16,384 | 63 | 64 | zero |

The kernel, unchanged fixed acceptance test, and reference `ops.cu` compiled
and linked for all three targets. `cuobjdump -lelf` confirmed each executable
contains cubins for its intended architecture. Running each executable on
the cloud host returned 77, `no CUDA device: skipped`. This is not a
numerical acceptance pass. Runtime source hashes were checked before and
after the compile matrix.

Grouped sm_86 PTX has no scalar shared publication stores. Its eight static
16-byte stores represent two A plus two B stores in each of prologue and
loop publication sites. The steady-state stage therefore publishes B with
two vector stores instead of eight scalar pair stores. Matrix instruction
counts remain 32 MMA, four x4 A ldmatrix, and sixteen x2 B ldmatrix per K32.
After normalizing only the compiler-generated anonymous-namespace symbol,
sm_86 quantization and both narrow kernel PTX entries are byte-identical to
the control. SASS was not verified: this toolchain lacks `nvdisasm`.

`python src/ds41/kernels/k2/validate_packet_publication.py` passed:

- Complete A/B ownership and physical-address uniqueness for all three
  specializations; aligned contiguous vectors and shared-memory bounds
- 438 partial-row/column stages and 773,120 consumer K8 vectors checked
  against the control's logical operand fragments
- Global vector alignment/bounds for six K values; every N tail and packet
  scale guard at three column tile bases
- Publication bank-service arithmetic and a deliberately incorrect XOR
  negative control
- The existing 1,681 CTA-grid bijections, integer product/tail/K=0 checks,
  and 56,134 finite FP8/power-of-two operand exactness checks

The supplemental `validate_packet_decode.cu` is a CPU-only CUDA-header
probe. It checked 65,536 eight-value packets, or 524,288 BF16 values, over
all 256 FP8 encodings and 256 E8M0 scale bytes in every packet slot. The
control pair conversion and new raw-word packaging matched bit-for-bit,
including NaN and signed-zero encodings. It does not execute device code.
Compile it with the same CUDA/host flags and the toolchain's CUDA library
path, then run the executable on the CPU.
