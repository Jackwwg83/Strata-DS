# K2-13: unscaled BF16 operands and K32-scaled partials

Base: feature/ds41 `c8c41ce1f0f4cd08969243d58294a850ee914fd0`.
The packed-input pipeline and output tile mapping come from the measured
K2-07 control `b965be65ca65fd577835cb976829b41735d787ce` (3650 us).
K2-04 `2ded5cd2d420b1441b42f504b586644b09bd92e9` provides prior GPU evidence
for scale-boundary decomposition, but uses native FP8 tensor cores. This
variant uses BF16 tensor cores on sm_86, sm_89 and sm_120 alike.

## Mechanism and storage

Activation quantization retains the reference's warp maximum, 1e-4 floor,
round-up-to-power-of-two scale, clamp and CUDA E4M3 conversion. It stores each
unscaled FP8 value exactly in BF16 and its row/K32 scale separately. Packed
weights decode directly into unscaled BF16 shared tiles. Each accumulator
partial starts from zero, combines exactly two K16 MMAs, and is multiplied
by its row and weight-block scale before joining the running FP32 result.
Different K32 scale blocks never share an unscaled partial.

The caller workspace layout is:

- BF16 activations: bytes `[0, 2*M*K)`
- FP32 activation scales: bytes `[2*M*K, 2*M*K + 4*M*K/32)`

Total is `17*M*K/8 = 2.125*M*K <= 4*M*K`. K is a multiple of 32, so the
scale array is aligned without padding. There is no additional global scratch
or mutable process state. Both launches use the supplied stream. Eager and
graph calls have the same path, with no allocation, free, device query,
host copy or host synchronization. Independent calls need their own interface
inputs/outputs/workspace, with no additional shared-state constraint.

Three packed asynchronous stages use 33,632 bytes shared for the 64x128
large tile; the two small-grid specializations use 16,864 and 13,600 bytes.
A wait followed by a CTA barrier makes the packed input visible; a second
barrier publishes decoded weights; a final barrier protects A and decoded-B
reuse. Zero-filled lookahead stages keep the wait-group count fixed. Copies
are drained before the epilogue and any fallback begins.

## Range safety and fallback

Every unscaled finite E4M3 operand is exactly representable in BF16. Nonzero
products are multiples of 2^-18, and a K32 sum has magnitude below 2^23. The
fast path requires individual scale exponents in [-117,118] and their sum
in [-108,104]. These sufficient bounds prevent operand-dequantization and
partial-scaling FP32 underflow/overflow. The combined power of two is built
from the checked exponent; it is never formed by multiplying two possibly
underflowing or overflowing scales.

Outside those bounds, or after nonfinite accumulation, the owning warp
recomputes its complete output rectangle with the original FP32 conversion
and per-lane K loop, followed by the original shuffle-down reduction. It
reconstructs the activation as `float(unscaled_bf16) * activation_scale`,
which exactly equals `float(fp8) * activation_scale`. Weight conversion uses
the original CUDA scalar E4M3 conversion and `ldexpf`. The fallback therefore
preserves subnormal scaled operands, E8M0 byte 255, NaNs, signed zero and
intermediate overflow behavior without introducing scaled BF16 rounding.
The whole-warp decision and warp-uniform row/column loops keep shuffles
converged. No CTA barriers follow the decision.

## Validation performed in the cloud, without GPU execution

CUDA 12.8 C++17 object compilation passes for sm_86, sm_89 and sm_120.
Ptxas reports zero spill loads/stores and zero stack for every final kernel.
The large tile uses 128 registers on all three targets; this exceeds the
strategy's 104-register estimate. The two-CTA launch bound avoids the spills
observed with the original three-CTA bound or a hard 104-register cap.
Small tiles use 82–96 registers; quantization uses 22–24.

`unscaled_host_test.cpp` passes using CUDA's host conversion routines:

- All 256 FP8 encodings by all 256 E8M0 bytes preserve scaled conversion
- All 65,280 finite BF16 inputs in mixed-sign/range quantization blocks
- 36,608 exponent-grid dot cases, including 25,245 exact fallback cases
- Independent K32 scales, cancellation, sparse operands and K=32/96/1280/5120/8192
- Worst modeled BF16-output row relative L2: 0.000507653, below 0.002
- 270 output-ownership layouts covering M/N tails, including M=77
- Workspace bounds through M=16384, and K=0 output ownership

A simple host build uses `g++ -std=c++17 -O2`, with CUDA and CCCL include
paths; no CUDA runtime linking or GPU is needed. The host dot model cannot
emulate tensor-core internal summation order. The fixed GPU acceptance,
performance ranking, non-default-stream capture/replay, and concurrent-call
checks remain untested locally and must be established by external execution.
No speedup or GPU acceptance is claimed by these compile/host checks.
