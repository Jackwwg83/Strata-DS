# K3-21: register-Q integration into the K3-11 sliced kernel

This is an integration ablation, not a new query-cache design. The control is
K3-11 commit `1a4598be4361c03ed818ab80f777f20c73fd4c6d`, whose published queue
score was 51.71 us. No GPU result is claimed for this candidate here.

## Change and invariants

Each CTA still owns eight heads, 128 keys per online-softmax tile, and 128 output
dimensions. Four warps retain the same key and output ownership. The two
XOR-swizzled 128-by-64 KV buffers retain the same gather packets, asynchronous
commit/wait points, cyclic QK reduction order, and final two slices for PV.

The shared Q array and its repeated Q `ldmatrix.x2` instructions are removed.
The QK B fragments are loaded once into registers before the key loop. The
slice loop is unrolled to give every fragment a compile-time index. To meet the
112-register budget without spills, the eight-packet inner gather loop is rolled
rather than unrolled. This changes loop-control overhead, not its packet order,
addresses, masking, or the slice-level overlap. The kernel uses `__maxnreg__(112)`
instead of the control's occupancy launch bound.

There is no scratch allocation, host synchronization, default-stream launch,
global arena, seed-specific branch, or numerical conversion added. Probabilities
are still rounded to BF16 before PV, and the sink only enters the unrounded final
denominator. The interface, fixed acceptance test, and reference remain unchanged.

## Exact Q ownership

For an `m16n8k16.row.col` BF16 MMA, let `lane = 4*h+t`, with `h` in 0..7 and
`t` in 0..3. B register 0 contains Q head `h` at K coordinates `2*t` and
`2*t+1`; register 1 contains coordinates `2*t+8` and `2*t+9`. Add the current
cyclic slice and K=16 step to these coordinates.

K3-11's non-transposed `ldmatrix.x2` loads precisely these pairs: address lanes
0..7 supply the eight rows of its first 8-by-8 matrix, and lanes 8..15 supply
rows of the second. K3-21 loads the same aligned packed 32-bit words directly.
No BF16 conversion, reordering of MMA operations, or reconstruction is involved.

For every warp and output rotation, every one of the 8*512 Q values has exactly
one owner. One lane owns 128 BF16 values, one quarter of a single head, as 64
packed registers. Each of the four consuming warps needs the same Q tile; the
64-register per-lane cost is therefore real, rather than the initial 16–32
register estimate. No lane stores a complete query. `register_q_proof.py`
independently checks the old shared/ldmatrix mapping against the new direct
mapping for unique labels and arbitrary 16-bit patterns.

## Local validation

CUDA 12.8, C++17, `-O3`:

| Target | Registers/thread | Shared/CTA | Stack | Spill stores/loads |
|---|---:|---:|---:|---:|
| sm_86 | 111 | 37,472 B | 0 B | 0 / 0 B |
| sm_89 | 111 | 37,472 B | 0 B | 0 / 0 B |
| sm_120 | 111 | 37,472 B | 0 B | 0 / 0 B |

Shared memory falls by 8,320 bytes from 45,792 bytes. On a 100-KiB shared-memory
SM, this still permits two CTAs rather than three: 3*37,472 = 112,416 bytes.
Registers also permit those two 128-thread CTAs. Thus this is not a claimed
occupancy improvement. Q is loaded by four warps instead of loaded once to
shared memory, so startup global-load traffic and gather-loop overhead are real
tradeoffs against eliminating repeated shared Q reads.

Validation performed before publication:

- Fragment ownership/bit identity, four output rotations and all four warps: pass
- Generated sm_89 PTX: all 64 Q loads precede key processing; 64 QK MMAs consume
  these registers; all eight remaining `ldmatrix.x2` instructions load PV
  probabilities; no PTX local-memory instructions
- Generated PTX: eight gather commits/waits preserve next-gather-before-current-
  slice-MMA overlap, with 64 QK and 16 PV MMAs per key tile
- Unchanged arithmetic CPU model: all six acceptance shapes, ragged lengths
  0/1/17/127/129/255/257/1023, all-negative lists, duplicate/boundary indices,
  zero/negative/larger scales, and extreme finite sinks pass; maximum modeled
  relative L2 error is 0.0019293952160053846
- Unchanged pipeline model: 200 randomized warp/asynchronous-copy completion
  schedules pass across two key tiles, including score/probability aliasing
- `git diff --check`: pass

These are compile-only and CPU/generated-code checks, not GPU execution.
The fixed RTX 4090 acceptance result, timing, and actual graph replay have not
been tested locally.
